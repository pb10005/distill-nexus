# 要件抽出

## 大原則: 人間に白紙を書かせない

「要件を過不足なく提示してください」は失敗します。人間は白紙から完全な要件を書けません。書けるなら最初からそうしています。

代わりに、**あなたが先に全項目を推測で埋め切り、人間には差分を否定してもらいます。** 書くコストより否定するコストの方が桁違いに低い。これが唯一の実用的な抽出方法です。

したがって、質問は「どうしますか？」ではなく必ず「**Aにしますが、違いますか？**」の形を取ります。

## 手順

### 1. 骨組みを作る

```bash
npx tsx scripts/spec-init.ts <slug> --title "..."
```

### 2. TBD を全部埋める（人間に聞く前に）

依頼文・既存コード・類似機能から推測して、`intent` / `out_of_scope` / `acceptance` / `assumptions` を埋め切ります。**この時点で人間に何も聞きません。** 確信が無い箇所も空欄にせず、最も妥当な案を入れて `assumptions` か `open_questions` に印を付けます。

受入基準を書くときの制約:

- `then` には**外から観測できる結果**を書く。「〜に対応する」「〜できる」は不可。「401を返す」「一覧に表示されない」が可
- 異常系を最低1件入れる。ハッピーパスだけの要件は必ず後で破綻する
- 非機能要件は `kind: nfr` にし、数値としきい値を書く（「高速」は要件ではない）
- 「かつ」で複合した `then` は分割する。片側だけ失敗した時に原因が特定できなくなる

`out_of_scope` は必須です。ここが空の要件は、実装が際限なく膨らんでも誰も止められません。**「今回やらないこと」を3つ挙げられないなら、まだ機能の輪郭が掴めていません。**

### 3. 機械検査

```bash
npx tsx scripts/spec-lint.ts specs/<slug> --questions
```

曖昧語・観測不能な `then`・異常系の不在・数値なし非機能要件を潰します。`--questions` は各欠陥に対応する質問文の型を出します。**ここで潰せるものを人間に聞いてはいけません。** 人間の注意力は有限で、機械が判定できることに使わせると本当に聞くべきことへの回答精度が落ちます。

### 4. 質問する（最大3問）

残った未決のうち、**影響度 × 不可逆性**が高い順に**最大3問**だけ聞きます。

優先度の判断:

- **高**: 後から変えるとデータ移行や再設計が要るもの（データモデル、認証方式、公開API、課金）
- **中**: 変更コストが実装数時間のもの
- **低**: 後からいつでも変えられるもの → **聞かずに `assumptions` に入れて進める**

質問の形式は必ずこれです:

```
Q1. 未登録アドレスへの応答
    → 200に統一します（列挙攻撃対策）。これで進めます。
    違う場合: 404を返す / エラー文言を変える
```

「決めないなら既定で進む」ことを明示します。人間が沈黙しても止まらない設計にしてください。3問を超える場合、超えた分は既定値のまま `assumptions` に入れ、`owner` と `resolve_by` を設定します。

### 5. 回答を三値に振り分ける

| 回答 | 行き先 |
|---|---|
| 明確な答え | 受入基準へ反映し、該当 `assumptions` を `confirmed` に |
| 「たぶん」「一旦それで」 | `assumptions` に `status: assumed` で残す。コード側に `@assumption AS-XXX` を付けさせる |
| 「わからない」「保留」 | `open_questions` に `default` 付きで積む。既定で実装は進める |

### 6. freeze

```bash
npx tsx scripts/spec-lint.ts specs/<slug> --gate freeze
```

freeze ゲートでは曖昧語・観測不能な then・異常系の不在・owner なし仮決めが **error に昇格**します。通ったら `status: frozen` にして実装へ渡します。

`open_questions` が残っている状態では freeze できません。確定させるか、既定値付きで `assumptions` に降格させてください。

## 禁止事項

- 質問リストを丸投げすること（「以下について教えてください」の箇条書き10項目）
- `out_of_scope` を空のまま実装に進むこと
- 曖昧語を要件に残すこと。「適切に処理する」は検証手順に落ちず、後で必ず解釈が割れる
- 未決を空欄のまま放置すること。空欄は「無い」ではなく「誰も見ていない」を意味する
- 人間の回答を勝手に `confirmed` に格上げすること。「一旦それで」は `assumed` です

## 実装へ渡した後

要件は凍結後も変わります。検証で出た差分は `/reconcile` で要件側に戻してください（`conformance-verify` スキル）。要件ファイルが実装から乖離した時点で、以降の検証は全部無意味になります。
